# 案例：一个桌面应用（Eas-Term）的设计系统事后补救

这是 `design-system-first` 的参考材料，**不是前提条件**：主文档的方法不依赖任何具体项目。这里记一次真实做过的完整过程，给你一个量级感和可照抄的做法。项目类型：桌面应用（Electron + React），按「完整」档做。

## 起因：开工时没先定标准

事后审计量到：字号 34 种、圆角 23 种、padding 23% 是奇数、同一个 424 宽的抽屉五页的页边距各不相同、z-index 52 种、box-shadow 128 种写法。这些都不是谁做错了，而是每个页面各自定了一份。事后统一要审计、拍板、迁移、对照验证，成本远高于一开始就定。

## 做法（审计 → 决策码 → 迁移 → 守卫）

1. **审计**：全仓 CSS 静态扫描按功能区归并（字号 / 字重 / 圆角 / 内边距 / 高度 / 颜色），再用真机探针量计算样式。数字出口径前先核对口径——别把登记的例外文件算进违规。
2. **汇报页 + 决策码**：本地 HTML 做可视化对照，每个取舍给默认值，用户复制一行决策码回来（`字阶=A · 范围=B · 例外=A`）。
3. **迁移**：postcss AST codemod（只改声明值，格式不动），先 `--dry` 报数，按维度分批；平局规则写死（半像素向上、14→12 向小）。
4. **守卫**：进 `npm run check`，按文件基线只减不增；新文件字面值为零；例外单一来源。
5. **对照验证**：同一脚本前后各跑一遍，逐界面比像素与计算样式，肉眼看截断 / 溢出；中英 × 暗亮四组合。

## 选型语料的局限

借鉴现成设计系统时用过一个 354 套的 token 语料库：字号阶只有 13% 的条目有、动效 7%、控件高度 1%、z-index 0%。**它只能给气质（颜色、圆角尺度、字体风格），不能代替细粒度维度。**

## 踩过的验收坑

- **脚本点得太早**：「视图看板」打开后没等渲染就量，截图其实是空对话，看板从没被量到过，早期所有看板对照都不成立。每个界面截图后要看一眼是不是想要的界面。
- **参数静默失效**：zsh 里 `set -- $combo` 不拆词，`--lang "zh dark"` 会静默回落默认，两组数据其实一模一样。两组数据完全一致时先怀疑参数没传进去。
- **空状态不等于验过**：看板 / 甘特 / 用量页都要在有数据的状态再量一遍。
- **数字口径**：把登记的例外文件算进违规，会让「还剩多少」虚高。
